# 30 分钟静默检查与续推门禁

用户目标是：网页任务连续 30 分钟没有有效进展时，先确认没有进行中的工具与未知结果，再带原目标和具体下一步继续推进。

**本版本不能把“页面没有变化”当作业务停滞，也没有经过认证的远端 owner 状态接口。因此这里只实现可审计的本地建议，不发送续推、不创建新意图、不重发旧任务。** evaluateIdle 是无 I/O、无定时器的纯函数；调用它不代表已启动后台监控或已执行真实平台任务。扩展可以由显式检查或本地状态检查调用，但不能绕过下面的门禁。

## 观察、时间与去重

- 仅检查已经尝试的 sending / sent / unknown 意图；本地排队和已取消意图不会被说成远端无进展。
- 锚点为 lastObservedProgressAt，否则使用 attemptedAt。前者只表示调用方记录的一次本地进展证据变化，**不等于已核验有效业务进展**。没有该记录时使用首次尝试时间。
- 页面刷新、重复查询、lastObservedAt 或 poll.nextAt 不会重置锚点。回查没有结果不是未执行证明。
- 精确达到 30 分钟后才生成建议。时间无效、锚点在未来或前次建议时间在未来时停止判断，报告时间问题。
- 同一 intent + anchor 具有稳定 suggestionId，重复检查复用原 createdAt 和建议，不追加无限审计记录，不重复通知。
- 锚点变化后的新建议至少距前一建议 30 分钟。冷却不授权发送，也不会改变 unknown。

调用方应按 suggestionId 保存一份建议，并仅在新的到期 suggestionId 出现时通知用户；不是每次轮询都弹提醒。扩展 controller.idleCheck 已持久化到期建议和审计，按稳定 ID/内容去重；UI 提供手动检查。纯函数本身不持久化，也没有后台定时检查/通知服务。

控制器应仅把 blocked-* 到期结果保存为 lastIdleProposal，并在后续检查中传回；not-due 检查结果可单独展示，但不能覆盖上一条到期建议，否则会丢失冷却锚点。任何审计增长都应按 suggestionId 去重并设置上限。

## 状态与权限

所有返回值都有 eligible: false、autoSendAllowed: false、requiresUserConfirmation: true：

| status | 含义 |
|---|---|
| not-due | 尚未到期、不是已尝试任务、冷却中或时间证据不足 |
| blocked-unknown | 存在发送、路由或 producer 未知；必须先查原任务，绝不续推 |
| blocked-running | 已观察到排队或运行中的工具/producer；不能假定卡死 |
| blocked-needs-authoritative-status | 当前没有经过认证的 owner 状态接口，即使页面 JSON 声称完成也不能放行 |

本版本不会产生 pending-user-confirmation 这一可发送状态。传入对象中的 verified: true、来源标签、用户选中的回执 JSON 或上一次建议里的可发送标志，都不能制造权威性。

## 建议内容

到期建议保留原目标，并给出具体下一步：

1. 在原聊天、原 invocation/provider 标识下进行原生只读回查，不创建新任务。
2. 独立确认没有进行中的工具、没有 unknown；仅“查不到”不满足这个条件。
3. 用户审阅明确下一步与完整续推文案后，再单独授权后续动作。

草稿带有“待核验、不得直接发送”标记。它不是运行指令或自动重试请求；不应被控制器送入现有发送队列。

## 未来可执行续推的必要条件（本版本未实现）

必须另接经过授权和身份核验的原生 owner 只读状态，准确关联原任务，并核对：

- 没有尚在排队/执行的工具或 producer。
- 没有未知、超时未确认或不可确定的发送/执行结果。
- 已有可审计的真实进展时间与终止/等待原因，而非聊天文字或页面动画。
- 用户已批准续推的目标、范围、具体下一步、目标聊天和完整消息。
- 续推拥有独立的通信意图 ID、一次发送屏障、冷却和回执观察；不更换原业务幂等键来冒充新的任务。

未满足这些条件就保留建议与阻断原因。即使满足了状态核验，授权也不能从页面内容推导。真实 ChatGPT → WorkSpace → producer 的空闲检测与续推端到端仍待单独验收。
